## Decisions the brief did not settle

**1. Migration 0005 exists at all.** The brief said two tasks and this is a
third. The screens need schema the repo did not have: the first account cannot
create its own `app_user` row, because `app_user` is admin-write and `is_admin()`
reads `app_user`, so the very first sign-up is locked out of the row that would
let it in. Locations had no `kind`. Nothing enforced T0-4 at the write path.
Nothing generated inferred history. Adding all of that to a client would have
broken the hard rule added in this session's own second commit, so it went into a
migration. If the extra migration is unwelcome, the thing to push back on is the
scope, not the placement.

**2. Effect lives in `attributes` with a check constraint, rather than in a
column.** The brief drew it under attributes and that is where it is. The
constraint listing the four values is what makes it fixed tier, and it fails with
a readable message rather than a cast error.

**3. Term references use a composite foreign key.** `unique (id, kind)` on `term`
plus a constant generated column on each referencing table means the database
refuses a cooper where a variety belongs. It costs one stored column per
reference and it was tested before being adopted. The reasoning is the inverse of
S-4: `event.subject_id` cannot be a foreign key and `doctor` has to carry it, so
where the check is possible it is worth taking.

**4. `event_type` was dropped too.** The brief's term section says "drop the two
enums" while its problem statement names three. Leaving `event_type` would have
left operations in the fixed tier, which is the whole point of the section, so
`event.type`, `task.type` and `template_step.type` are all operation references
now.

**5. `next_cap_action` returns a row rather than an enum.** It returned
`event_type`, which no longer exists. It now returns the operation's id, value
and label, so a caller can write the event without a second lookup and show the
label without a third.

**6. `template.variety` became a term reference, in 0005.** 0004 migrated the
node and vessel columns and left this one as text, which meant matching a
template to a lot compared text to a term value, where a typo yields no template
and no error.

**7. `tests/schema_assertions.sql` was written.** CLAUDE.md's definition of done
has always named it and the file has never existed, so the `psql` line of that
block was a description rather than a command. Twenty-eight assertions now, in one
transaction that rolls back, runnable with `bun run db:test`.

**8. Term writes stay admin-only.** Add-inline therefore needs an admin. The walk
is admin work, so this is correct today. It becomes wrong the first time a cellar
user needs a cooper mid-intake, and the fix is one policy line.

**9. `setpoint_change` carries effect `measurement`.** The spec is careful that a
setpoint is a decision and a reading is an observation. Effect answers only what
happens to volume and lineage, and for both the answer is nothing. This is the
case S-15 exists to name.

**10. Compost C-6 was added so a grade kept its meaning.** The brief asked for
term configuration screens to be noted as deliberately absent. The status ledger
grade for that is Deferred, and Deferred is defined as naming a compost entry, so
using the word without writing the entry would have quietly devalued it
everywhere else.

**11. Manual code entry sits beside the camera, not behind it.** A phone with a
wet lens in a dark barrel room is not an edge case.

## What was verified, and how

A scratch Postgres 16 with a minimal Supabase auth shim, and `auth.uid()` reading
a session claim so the assertions can act as a named account.

`tests/schema_assertions.sql`, twenty-eight assertions, all passing:

- all five migrations apply clean, in order, from empty
- a variety, cooper, wood, vessel type and location kind added at runtime with no
  migration
- an operation effect outside the four is refused
- a cooper is refused where a variety belongs
- no node can exist before the facility party does, and only one facility party
- the first account becomes admin, the second becomes cellar, claiming twice
  returns the same account
- neither a node nor an event can be born confirmed
- an operation the kernel has never seen records and changes no lineage
- `topping_check` refuses a vintage mismatch, and stops refusing it when vintage
  is dropped from the operation's predicate, with no code change
- rebinding a code adds nothing, both codes on a barrel resolve to it, and a
  bound code refuses to move to another barrel
- vessel, lot, placement and two codes in one action, visible on the vessel page
- with no template, no history is invented; with one, history appears and every
  event of it is stamped inferred
- a cellar user may not confirm; a verifier may
- a cellar user is refused locations, vessels and terms, and allowed events
- a cellar user linked to no party sees the whole cellar
- a client login sees the one lot it owns and none of the other six

The commit message on `3cde9a0` says twenty-nine, which was a miscount made while
writing it. The file has twenty-eight assertions and all of them pass. Recorded
here rather than corrected in history, because the history is what it is.

Client: `bun run typecheck` and `bun run lint` clean, `vite build` succeeds, and
the built app boots in a 390 pixel viewport with no page errors and no horizontal
scroll.

## What could not be exercised, and is therefore yours to test

This session runs in an isolated container. Docker on your machine is not
reachable from it, so the Supabase CLI being installed there does not make it
runnable here. It was checked at the start of this session and again at the end.

**`supabase db reset` was not run.** Still the outstanding acceptance criterion
from session 1, still open, and not claimed on the `psql` route.

Everything below is written, typechecked and built, and has never met a running
Supabase. When you walk the cellar, these are the things being tested for the
first time rather than re-checked:

| What | Why it is unproven |
|---|---|
| Sign up and sign in | GoTrue has never issued a token to this client. If the instance requires email confirmation, the sign-up screen says so and the flow expects you to confirm and come back |
| `claim_account` through PostgREST | Asserted in SQL. Over the wire it is a composite-returning function, and PostgREST renders those as a bare object while set-returning ones come back as an array. The client accepts either rather than betting, but the bet has not been settled |
| The facility screen | Its whole job is explaining a wall you hit before anything exists. Whether the explanation lands is a thing only a first run can tell you |
| Photo upload | Bucket creation is guarded on the storage schema existing, and that guard skipped in every run here. The bucket, its two policies, the upload and the signed url are all unexercised |
| The camera | zxing has never seen a camera in this container. Manual entry is beside it precisely so a camera failure is not a dead end |
| `create_vessel_with_wine` over the wire | Verified by direct SQL. Its two jsonb payload arguments have never been mapped by PostgREST |
| RLS through a real JWT | The assertions set the `sub` claim directly. GoTrue issuing a token and PostgREST mapping it to `authenticated` is the part still assumed. This is what remains of S-7 |
| Inferred history, end to end | `generate_inferred_history` is asserted, and no template is seeded, so a real walk will show zero generated events for every variety. That is S-17 behaving correctly, not a fault |

If the walk breaks, the most likely places are the four wire-format rows above,
in that order.

## What session 1 claimed, and what actually happened

You could not `bun install` after cloning, and session 1's report lists
`typecheck` and `lint` passing on the empty workspace as verified. Both are true,
and the explanation is neither of the two you offered.

`git log --diff-filter=A -- package.json tsconfig.json biome.json` returns one
commit, `c6a04a3`, which added all three. They were tracked, and they are in that
commit's tree. The checks did pass and the files were committed.

What a fresh clone gets is `origin/main`, and `origin/main` contains exactly one
file: `LICENSE`. Every commit of both sessions, twenty-one of them now, lives on
`claude/sql-files-to-markdown-i31rob`, which has never been merged. A clone
checks out the default branch, finds a licence and nothing else, and `bun install`
says what it said.

So this is not an undelivered acceptance criterion. It is a real problem of a
different kind, and it is worth recording because it will keep happening: the
acceptance criteria of both sessions describe a working tree, and nobody has
checked what a stranger gets from the default branch. That stranger is the
acceptance test this session's brief cares most about, and right now they get a
licence.

*Recommended:* merge the branch to `main`, or make the walk's acceptance test
start from a fresh clone of the default branch rather than from a working tree.
The second is the version that keeps being true.

## Found while answering a question, after the report was written

`supabase/config.toml` set `enable_signup = false` under both `[auth]` and
`[auth.email]`, written in session 1 on the reasoning that a winery app has no
public sign-up. That reasoning is right about a running winery and wrong about a
fresh install: the first account has to be creatable and there is nobody to
create it for you, so the setting made step one of the first-run walk impossible.
Local development now allows signup, and closing it is a decision for the hosted
project once an admin exists.

Worth noting how it was found. It was not found by any check in this session,
because every check ran against `psql` and none of them went near GoTrue. It was
found by reading the config while answering a question about something else. The
unverified table above is the honest list; this is a reminder that the list is
where the bugs are.

## For whoever picks this up next

The kernel now decides four things a client might have been tempted by: whether
an account is admin, whether a top is compatible, what history a template
implies, and what happens when a vessel and its wine are created together. If a
screen ever needs a fifth, it goes in a migration.

`bun run db:test` is the fastest way to find out whether a schema change broke
something. It rolls back, so it is safe against a development database and
useless against production.
