## Decisions the handover did not settle

Each of these is a place where the documents ran out and something had to be
chosen. They are listed so that disagreeing with one is cheap.

**1. `node.owner_id` is not null and defaults to the facility party.** The
consequence is an ordering constraint: no node can be inserted until the Stage 0
walk creates the facility party, because the default resolves to null and the
column refuses it. Taken deliberately. A lot nobody owns cannot be reported on,
and a nullable owner would surface that ambiguity at the worst moment rather
than the earliest one. The alternative, seeding a facility party in the
migration, was rejected because the winery's own legal name is not a migration
file's to invent.

**2. Exactly one active facility party, enforced by a partial unique index.** It
is what makes the default above unambiguous. A second facility is the deferred
`org_id` problem, not a second row here.

**3. All three views switched to `security_invoker`.** A Postgres view runs as
its owner unless told otherwise, so `lot_state` would have handed a client every
lot in the cellar through the back door while `node`'s own policy refused it.
Without this the client-scoped policy in 0003 would have been decorative. This
was not in the brief and is the change most worth a second opinion, because it
also changes how the two views written in 0002 behave.

**4. `product_type` defaults to `wine`.** The brief named the enum and not the
default. A not-null column with no default would break every insert; wine is the
overwhelming case at this facility. Cheap to revisit while the table is empty.

**5. `bind_vessel_code` and `resolve_vessel_code` as database functions.** The
brief described the behaviour (rescanning is not an error, a bound code returns
its vessel) without saying where it lives. It went into the database because the
uniqueness rule it enforces lives there, and the same logic in a client would be
a second place for it to be wrong.

**6. Vessel codes are admin-write.** Codes are bound during the Stage 0
inventory walk, which is structural work, so this matches `vessel` itself rather
than the event tables. If interns end up labelling barrels, this is the line to
change.

**7. Raw counts removed from prose.** The status ledger said six load-bearing
sorries and CLAUDE.md said seven sorries and three load-bearing; the two
disagreed with each other before this session started, and both would have gone
stale again the moment S-8 landed. Both now point at the ledger instead of
restating it. This follows the status ledger's own rule applied to the sorry
ledger.

**8. The spec's dependency on `docs/design-axioms.md` was removed.** That file
does not exist and never did in this repository. The axioms are section 1 of the
spec itself, so the field is now empty rather than pointing at nothing.

**9. `src/index.ts` instead of `src/.gitkeep` in the three packages.** A
deviation from the requested layout. `tsc` refuses a config whose `include`
matches nothing (TS18003), and the alternative was a tsconfig pointed at an
empty file list, which passes forever while checking nothing. Each file is
`export {}` and a comment. It is not UI and it is not logic.

## What was verified, and how

A scratch Postgres 16 cluster with a minimal stand-in for what Supabase provides
(`auth.users`, `auth.uid()`, the `authenticated` role, the
`supabase_realtime` publication).

- All three migrations apply clean, in order, from an empty database.
- Both codes on one barrel resolve to the same vessel.
- Rebinding a code the vessel already carries is idempotent and adds no row.
- A code bound to one barrel refuses to move to another.
- A second facility party is refused.
- `node` refuses to insert until a facility party exists.
- A node owned by a client and a node owned by the facility both round-trip.
- `bun run typecheck` and `bun run lint` pass on the empty workspace.
- `bun run doctor` exits non-zero naming sorry S-4.
- Ten headered files, twenty-eight dependency edges, every edge bidirectional,
  checked by script rather than by reading.
- Every `.env` variant, `supabase/seed/*.local.sql`, `uploads/`, `photos/`, and
  database dumps confirmed ignored by `git check-ignore`.
- No em dashes in any tracked file or any commit message.

## What was not verified

**`supabase db reset` was never run.** The Supabase CLI is not installed in the
session environment. The migrations were applied with `psql`, in filename order,
against an empty database, which is the same sequence the CLI performs, but it
is not the same command and the acceptance criterion named the command. Run it
once locally before trusting it.

**The database major version is unconfirmed.** `supabase/config.toml` pins
`major_version = 15`; the verification above ran on Postgres 16. Both satisfy
the one version-sensitive feature used here, `security_invoker` on views, which
needs 15 or later. Set this to whatever the hosted project actually runs before
the first deploy, because a migration that applies on one major version and not
the other is a discovery best made locally.

**RLS.** Written, never exercised by a second account. This is sorry S-7, which
this session widened rather than duplicated: the client-scoped policy added in
0003 has exactly the same status as the ones written in 0002. Client scoping is
a policy, not a boundary that is known to hold.

## For whoever picks this up next

locations and vessels, then codes. Nothing else can be created before the
facility party exists.

order is by irrecoverability of failure and none of the section 8 additions are
irrecoverable.

be designed around in the meantime. S-12 is the one with a date on it: bottling
