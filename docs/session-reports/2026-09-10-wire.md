# 2026-09-09 and 10: the wire, and what was behind it

The session that answered the two open items from the walk report, and then kept
going because each thing built exposed the next thing missing.

## What was asked, and what happened instead

The brief was two items: run `supabase db reset` on a machine with Docker, and walk
the first run on a phone. Both closed in the first hour. Everything after that came
from the winemaker using the thing and saying what was wrong with it, which turned
out to be a better source of work than a plan.

`supabase db reset` applies all migrations clean from empty. `bun run db:test` passes
against real Supabase rather than the psql shim. The first run walked end to end on a
phone over Tailscale: sign up, claim, facility, vessel with wine, photo upload to
storage with a signed url, RLS refusing a cellar user through a real JWT. The four
wire-format rows the walk report flagged as most likely to break did not break.

## Four defects, and the pattern in them

**`vessel_state` did not obey row level security.** A view runs with its owner's
rights unless created `security_invoker`, and this one was not, while `lot_state` and
`task_board` were. Measured as a client with one lot: one row through `node`, one
through `lot_state`, two through `vessel_state`, including another party's lot by
name. Both custom crush clients could read the whole cellar from the screen they would
open first. S-26.

**A permission check answered null.** `current_party_id()` is null for everyone on the
crew, so `owner_id = current_party_id()` is null rather than false, `not null` is null,
and an `if` on null does not run. Two gates fell open for exactly the people they
existed to keep out.

**A security definer function repeated the first mistake.** `visible_node` redacted
fields correctly and never asked whether the caller could see the row at all. Caught
within minutes by the assertion written for S-26, which is the only reason it is a
paragraph here and not an entry in the ledger.

**Thirty four functions broke under a restore.** `pg_dump` empties `search_path` on
purpose, and an unpinned function then cannot resolve its own types. The error message
was confidently wrong: "field maker names vocabulary cooper, which does not exist",
true of the cast and false of the vocabulary.

The pattern is worth more than the four fixes. Every assertion in this repository
queried tables. Every screen queries views. So the policies were tested and the thing
the application actually reads was not, and the gap survived eight sessions. There is
now a check that every view in `public` is `security_invoker` and that every function
pins its path, which is the cheap version of the lesson.

## The thing that was not a defect but mattered more

The winemaker asked whether the app always has to destroy the data he enters. It did,
because `supabase db reset` was being run after almost every change, and CLAUDE.md's
definition of done named exactly that command. He had been holding off inventorying
the cellar because of it.

`bun run db:up` applies pending migrations and leaves data alone. CLAUDE.md now says
so and warns about the other one. `db:backup` and `db:restore` exist and were tested
by wiping and restoring rather than by assuming.

The restore is honestly imperfect and S-29 says why: migrations seed vocabulary with
generated uuids, so `chardonnay` is a different uuid after every reset and a restored
lot points at a variety that no longer exists. The same defect means local ids will
not match hosted ids on deploy.

## Assessment: five patterns from the commercial platforms

Requested as design work with nothing written into running code. Spec changes are
marked specified and none of it is built.

**1. Create and complete are different interfaces. Adapted.** The observation that the
board is a completing interface wearing a planning interface's clothes is correct.
Nothing in the spec described a human creating tasks at all: templates seed them on
stage entry and no person is in that loop. The fix is not a second board. Work orders
already exist in 8.2 as a grouping of tasks that exist, and the missing half is that a
work order is the thing that *creates* them, over a set of vessels chosen at once.
Section 8.2 now says so.

**2. Photograph the sheet. Adopted as specified, not approved.** It lands on machinery
that already exists: the image is stored as evidence, the reading proposes events at
`inferred`, and a person confirming is what stamps them, which is the delta-and-verify
boundary from section 6 and is already enforced by trigger. The cost is a vision
dependency, probably paid, which the standing rule says must be consulted on, and a
confidentiality question about sending a client's numbers to a third party. S-31.
C-1 now carries a pointer to it, because it is the same need reached by a route that
does not need an SDK or a native app.

**3. Coverage, not convenience. Adopted, and already proven once.** The target set was
not in the spec: topping mode had a session list, which is a record of what you did
rather than a set you must cover. It is now stated generally in section 5. It is also
already built, in `procedure_session`, which lays out one run per vessel in the order
given and can say which are unfinished.

Patterns 1 and 3 turned out to be one mechanism seen from two ends, and the spec now
says that rather than specifying two.

**4a. The facility dropdown. Rejected, C-7.** It is multi-tenancy, and this repository
answers custom crush with ownership inside one facility while deliberately deferring a
facility-level `org_id`. Adopting the dropdown would make `party` mean both who owns
the wine and which site you are looking at, and those come apart the first time a
client owns wine at two sites.

**4b. Takeout. Adopted, and it is the differentiator.** Section 8.6. Making exit cheap
is the one advantage here that a subscription platform cannot copy, because copying it
removes the reason their customers stay. The four hard parts are answered as far as
design can answer them: the boundary is an ownership change and it becomes a terminal
node stating what was acquired and from whom; vessel identity does not travel but
vessel shape does, reusing the distinction the privacy work already draws; import is
the same document loaded, and the untyped floor is what lets an unfamiliar vocabulary
land without grounding anything.

The fourth part is not answered and is the reason this is not close to free. An
imported event has no way to say who observed it: `by_user` references `app_user`, and
`has_an_author` refuses a row naming neither a user nor a sensor. A fourth provenance
value does not fix that, because the missing fact is identity rather than confidence.
S-32.

Export is much cheaper than import and should not wait for it. The traversal exists.

**5. Offline. The split still looks right and the line moved.** T1-2 said append-only
versus mutable. The session built writes that are neither: `rack` decides whether a
transfer moved a lot or made one, and `record_event` decides whether recording against
some of a lot's vessels forks it. Both are appends by effect and neither can happen
without the kernel, because doing them offline means a client reproducing the
decision. T1-2 has been restated as writes the kernel must decide about versus writes
it need not. S-30 holds what that leaves unanswered, which is what the app actually
does when somebody racks a barrel in a shed with no signal.

## The lot history screen: a day, and it is the honest answer

Everything it needs exists. `node_history` walks lineage with a cutoff per edge and
marks what was inherited. `node_bin_shares` and `block_composition` answer what it is
made of. The result screen already renders a history list with provenance tags and a
"before the split" marker, so the hard part, which was the recursive time-bounded
traversal, is built and asserted.

What is left is a screen: the history list it already renders, composition rendered
from a function that exists, a placement timeline which is a query nobody has written,
and a lineage view. Most of the day is the lineage and placement rendering, not the
data.

Worth noting why it might deserve to jump: the app currently records a great deal and
shows almost none of it back. That is a motivation problem for a crew being asked to
write things down, and it is the specific weakness reviews identify in both commercial
products.

## Does any of this change the build order

No, and intake stays first. Nothing assessed here is irrecoverable, which is the only
thing section 7 is ordered by. A missed bin cannot be reconstructed; a lot history
screen built in November is a lot history screen.

Two things are worth saying anyway.

The export half of takeout is also the portable backup that S-29 says does not exist,
because a document carrying a lot and its lineage without depending on generated ids
is exactly what a restore needs. That is insurance against a data loss risk this
session proved is live rather than theoretical, and it moves export out of "after the
vintage" and into "worth doing when there is a day".

And the lot history screen is a day. It does not go before intake. It is a good
candidate for the first pressing downtime, ahead of most of section 8.
