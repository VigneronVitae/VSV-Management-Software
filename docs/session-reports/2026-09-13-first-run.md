# 2026-09-13: the first run

W-8. The client had been typechecked, built, and never run. It runs.

Everything below was observed in a browser against an isolated Supabase stack with
real policies on, never against the cellar. The stack is the recipe in
`docs/first-run.md`, and it exists because `project_id` in `supabase/config.toml`
is fixed, so every clone on a machine drives the same containers.

## Predictions, scored

1. **A stranger stops at configuration; five to ten documented-path failures.**
   **Right about the count, six, and right about where it ends. Wrong about where
   it starts.** I predicted the break would be the link from `supabase start` to
   the client knowing a URL, on the reasoning that it was the one link that had
   never carried traffic. It is broken, and the stranger never gets that far,
   because `supabase` is not installed and the third documented step destroys the
   database.
2. **A refusal is indistinguishable from emptiness.** **Right in substance,
   wrong in shape, and the wrong shape is worse.** A denied read is silent, as
   predicted. But the client does not render emptiness. It renders content.
3. **Section B reproduces nine to thirteen of nineteen.** **Not scored. I reached
   five of the seventeen still open and did not finish.** See below; this is a
   partial phase and saying so is the whole of the honesty available.
4. **The undefined enumeration finds twenty to forty sites, under a third real.**
   **Wrong on the count, sixty one. Right that almost none are real.**
5. **At least one step appears to succeed and writes nothing.** **Wrong, and
   inverted.** No step in the walk did. What happens instead is a step that writes
   everything and appears to have written nothing.

## How far a stranger gets

`README.md` has three setup steps. Six things are wrong with them.

1. **The Supabase CLI is a named prerequisite and is not installed.** `supabase
   start` fails, and so do `bun run db:up`, `bun run db:reset` and `bun run
   db:test`, three of which appear in the definition of done in `CLAUDE.md`.
   `npx supabase@2.34.3` works and the README does not say so.
2. **Step three is `bun run db:reset`, which destroys every row**, with no
   warning. `CLAUDE.md` warns about exactly this in two places. The README, which
   is the file a stranger reads, does not.
3. **And it resets somebody else's database.** `project_id` is fixed, so the CLI
   derives container names from it rather than from the directory. A second person
   cloning onto the same machine and following the README wipes the first
   person's harvest.
4. **Nothing tells you to configure the client.** `apps/web/.env.example` exists,
   `packages/core/src/env.ts` throws a message naming it, and the README mentions
   neither.
5. **Nothing tells you to start the client.** `bun run dev` is in `package.json`
   and appears nowhere in the README. **The documented path does not run the
   thing the repository is.**
6. **`supabase/config.toml` names somebody's tailnet as `site_url`** with a
   comment saying a fresh clone must change it or sign-in breaks silently. That
   comment is correct and is not in the README either.

I stopped at 2, because following it would have destroyed the cellar. Everything
after that used an isolated stack.

**This count is a lower bound and I am not a stranger.** A real one can fail to
notice a step. I can only fail to notice that I knew it.

## The walk, both roles

Fresh install: 27 migrations, the vocabulary seeded from them, zero parties, zero
users. The client handles that. It asks for an account, then a name, then the
facility, and says why the facility comes first: nothing can be created before it
because every lot has an owner.

**As admin, the walk is clean.** Account, facility, vessel with wine, empty
vessel, rack. The database matched the screen at every step: the source placement
closed at 220, the destination open at 218, the lot's quantity down by the 2 L
loss, one `rack` event marked `observed` and authored. The rack preview is a call
to `rack_plan`, so what a rack means is the kernel's answer rather than the
client's, which is `CLAUDE.md`'s rule being followed rather than described.

**As a cellar user, everything is offered and some of it is refused.** The edit
screen shows a cellar hand every field on a vessel. Three are writable:
`has_glycol`, `setpoint_c`, `mode`. The client knows the role, renders "Sam,
cellar" at the top of the screen, and does not use it to shape the form.

## What a refusal looks like to a person

Three shapes. Only the first is fit to show anybody.

**A kernel `raise` arrives as its own sentence.** Changing a capacity as a cellar
user produces "a cellar user may not change vessel.attributes; ask an
administrator", rendered in the page. That is the kernel's voice reaching a person
intact, and it is the thing this project has been building toward.

It also names a column the person did not touch. I changed the capacity. The
client sends every key on save, so `update_vessel`'s "key present means set this"
contract makes each save a write to every column, and the trigger refuses on
whichever disallowed one it reaches first.

**An RLS denial on a write arrives raw.** Adding a client as a cellar user
produces `new row violates row-level security policy for table "party"`, on
screen, in front of somebody standing next to a press. PostgREST relays
Postgres's generic text and there is no sentence to relay instead, because a
policy has no message. The kernel's own refusals have human words. Its policies
cannot.

**A denial on a read arrives as nothing**, and that is where the session went.

## The client login, which is where the silence lives

A custom crush client with a login attached reads:

| Table | Rows they should see | Rows they get |
|---|---|---|
| `node` | 1 | 1 |
| `placement` | 1 | **3** |
| `event` | 0 | **1** |
| `vessel` | 1 or 3 | 3 |
| `app_user` | 0 | **3** |

`node_read` is scoped. `placement_read`, `event_read`, `lineage_read` and
`app_user_read` are `using (true)`. So the client cannot see the name of the
facility's lot and can see its every movement, volume and timestamp, the rack
event with its method and volumes, and the name and role of every member of
staff.

**`vessel_state` makes the client display it.** The view redacts `lot_name`,
`lot_owner_id` and `lot_owner_name` for a lot the viewer may not read, and does
not redact `node_id` or `current_volume_l`, because those come from `placement`
and `placement` is open. So the home screen tells a custom crush client that
**"2 of 3 have wine in them"** while they can name one of them.

**And deactivating an account removes the lot names and nothing else.** A
deactivated user signs in, gets the full home screen, and still reads every
placement, every event, every vessel and every account. Only `node` goes to zero.

None of this is new. **It is ledger A5**, filed EXPLOITABLE in the first review
round, naming `event`, `placement`, `lineage` and the rest by name. The run did
not find it. What the run adds is the price of it, in a sentence somebody can act
on: a client can enumerate the facility's volumes and movements through a view
built to hide them, and firing somebody does not stop them reading the cellar.

**The instrument had been printing this for three sessions.** Twenty `weaken`
mutations report "degenerate, changed nothing" in every run, and they are
degenerate precisely because those twenty policies are already `true`. The
exclusion list was the finding. It was in a column labelled excluded, and every
session including this one's four predecessors read past it.

## The confirmation screen, which is the worst thing here

Let the write succeed and the read after it fail. One GET, returning `[]`.

```
Saved

Vessel        unknown
Location      unassigned
Lot           unknown
Wine          unspecified
Volume        unrecorded
Whose wine    unrecorded
Codes         none bound
```

A complete success page. Every field a plausible blank. The header degrades from
"B06-READFAIL is on the books" to "Saved" and nothing else changes.

The vessel, the lot and the placement are all really in the database. I checked.

This is seven `vessel?.` expressions at `walk.ts:2016` to `2064`, each with a
sensible fallback, which together turn a missing object into a filled-in record of
nothing. Individually every one is defensive good practice. **The absent value
class does not need a comparison to be dangerous. It only needs enough defaults
in a row.**

Ledger B7 predicted the opposite failure, that a committed write would be painted
as a failure. It is painted as a success.

## The undefined class

`scripts/undefined-sites.sh` enumerates it: **61 sites over 3629 lines**, four
ordering comparisons, 32 `||` defaults, 25 optional chains. Committed at
`docs/review/undefined-sites.tsv`. Not a gate and not a score; W-8 forbids both
before the surface is known, and it is right to.

**Almost none are real, and the ones that are do not look like the ones I went
looking for.** I expected ordering comparisons, on the reasoning that
`undefined < x` and `undefined > x` are both false so a threshold permits from
both sides. There are four ordering comparisons in the entire client and three are
on an array's `length`. The 32 `||` defaults are almost all `field.value() || null`
on a string, where the empty string genuinely means not given.

The real ones are the two `current_volume_l` renders that swallow a zero, which is
B11, and the `vessel?.` cluster above. **The class is real and it arrived through
accumulated defaults rather than through arithmetic**, which is the opposite of
where four sessions of SQL nulls taught me to look.

The first version of this enumeration counted 14 ordering comparisons. Nine were
TypeScript generics: `Promise<{`, `Array<{`, `} | null>`. Requiring spaces around
the operator separates them, and an unspaced `a<b` would now be missed, which
biome's formatting makes unlikely and which is a stated limitation rather than a
hole.

## What was fixed, and what was not

W-8 says fix only what blocks a second walk. **Nothing blocked the walk.** So the
only fix is the README, which blocks a second *person*: it never starts the
client, and its third step destroys a database that may be somebody else's.

`docs/first-run.md` is the convenience: the six-screen walk, the queries that
check it, and the isolated-stack recipe. It says at the top that it is not
verification, because it is not.

## What needs a person

**Whether "2 of 3" is a leak or a feature.** A custom crush client seeing that
three vessels exist and two hold wine may be exactly right: they are standing in
the barn, they can count barrels. Whether they should be able to read the volume
in somebody else's is a different question and I do not know the trade the winery
wants. A5 is filed and unfixed; this is the question that decides how it gets
fixed.

**Whether a cellar hand should be shown a form they cannot save.** The edit screen
offers every field and permits three. Hiding the rest is easy and might be wrong:
seeing what an administrator would have to change is arguably the point.

## What I got wrong

**Prediction 5, inverted.** I predicted a step that appears to succeed and writes
nothing, at four for four in this project. What exists is a step that writes
everything and appears to have written nothing, and I would not have looked for it
if the enumeration had not put seven `vessel?.` expressions in one place.

**Prediction 4's count, by twenty one**, and its mechanism entirely.

**I did not finish section B**, and the scorecard phase 3 asks for is the one
number this session was best placed to produce. The run cost more than I budgeted
and I spent it on the leak rather than on the list. That is a defensible choice
and it is still an unfinished phase.

**I reported duplicate network calls to myself for several minutes** before
realising I had installed the fetch interceptor five times over, each wrapping the
last. An instrument that multiplies what it measures, found by noticing the
multiplier was five and there were five installs.

**I fast-forwarded `main` locally** because W-8's header names it, and left the
push unasked. The remote is still four commits behind, now five.
